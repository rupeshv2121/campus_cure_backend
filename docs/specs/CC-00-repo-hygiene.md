> **Scope constraint (team decision, 2026-08-16):** this is a shared repository with active
> collaborators. **No branch is renamed, deleted, or retargeted, and no remote setting is changed by
> this spec.** The branching observations below are recorded as a *proposal for the team to discuss*,
> not as work to execute. Everything in "Design" is additive and local.

## Problem

Three low-risk gaps that make onboarding and coordination harder than necessary:

1. **No `.env.example` in either repo.** A new collaborator cloning the project cannot tell what
   configuration is required. Backend needs `DATABASE_URL`, `FRONTEND_URL`, `JWT_SECRET`; frontend
   needs `VITE_BACKEND_URL`. Phase 1 adds several more AI keys, which makes this worse fast.
2. **Stale local build output.** `campus_cure_backend/dist/` contains `utils/autoRouting.js`,
   compiled from a source file that no longer exists in `src/`. It is correctly gitignored and
   untracked — this is a local-disk-only issue — but it misleads anyone reading the tree, and it
   already caused a wrong initial assumption about what the project does.
3. **These docs are untracked.** `docs/` has no version control and no backup.
   **RESOLVED 2026-09-20:** moved to `campus_cure_backend/docs/`, so they are versioned and pushed
   with the backend. Tracking alone would not have solved the stated risk — only pushing gets them
   off a single machine.

## Goal

A collaborator can clone either repo, read `.env.example`, and get running — and the tree contains no
compiled artifacts that contradict the source.

## Non-goals / Out of scope

- **Any branch or remote change.** No renaming, no deleting, no default-branch change, no branch
  protection. Explicitly excluded by team decision.
- `git init` at the project root. Docs stay untracked for now.
- Rewriting history in either repo.
- Merging the repos or introducing submodules.
- CI — that's CC-04.

## Design

### 1. `.env.example` in both repos

Key names and comments only. **Never values.** Committed, so it must be safe to read publicly.

`campus_cure_backend/.env.example`:

```bash
# Database — Supabase Postgres connection string (pooled)
DATABASE_URL=

# Origin allowed by CORS, e.g. http://localhost:5173
FRONTEND_URL=

# Minimum 32 characters. Generate: openssl rand -base64 48
# Must be set — the app refuses to start without it (see CC-01).
JWT_SECRET=
```

The backend `.gitignore` currently has `.env` and `.env.*`, which would swallow this file. Add an
explicit negation:

```gitignore
!.env.example
```

`CampusCure_Frontend/.env.example`:

```bash
# Backend API base URL, e.g. http://localhost:3000
VITE_BACKEND_URL=
```

This file is **the** place new configuration gets documented. Every later spec that adds an env var
adds it here in the same PR.

### 2. Clear stale build output

```bash
rm -rf campus_cure_backend/dist
```

Local only; regenerated by `npm run build`, already gitignored. Nothing is lost.

### 3. Recorded observations — for team discussion, not execution

Noted so the information isn't lost. **Do not act on these without team agreement.**

- `campus_cure_backend` has both `main` and `master`. `origin/HEAD` points to `origin/main`, which
  suggests `main` is authoritative, but the ambiguity is a real hazard: a push to the wrong branch
  fails silently. Worth confirming as a team which is live, and whether `master` holds unique commits
  (`git log --oneline main..master` — read-only, safe to run).
- Branches are per-developer (`austin`, `rupesh`) rather than per-feature. That works well at the
  current size. The roadmap's ~30 features have a real dependency chain — CC-11, CC-12 and CC-13 all
  require CC-10 to be finished — so at some point the team will need a shared answer to "is CC-10
  done?" A `develop` integration branch plus per-feature branches is the conventional fix, but it is
  a team decision with a coordination cost, and per-developer branches with clear ownership of spec
  IDs can work too.
- Whatever model the team picks, the coordination requirement is the same and is cheap to adopt
  today: **one owner per spec at a time**, declared before starting, and features that depend on
  another spec don't start until that spec's owner says it's merged.

## Acceptance criteria

1. `campus_cure_backend/.env.example` exists, is committed, lists all three current keys, contains no
   values.
2. `CampusCure_Frontend/.env.example` exists, is committed, contains no values.
3. `git check-ignore campus_cure_backend/.env.example` reports it is **not** ignored.
4. `campus_cure_backend/.env` is still ignored (`git check-ignore` confirms) and was never committed.
5. `campus_cure_backend/dist/` is absent from local disk.
6. No branch was created, renamed, deleted or retargeted; no remote setting changed.
   `git branch -a` output is identical before and after.

## Test plan

- **Manual:** `git status` in both repos shows only the intended `.env.example` and `.gitignore`
  changes staged.
- **Manual:** clone the backend to a temp directory, copy `.env.example` to `.env`, fill it, and
  confirm `npm install && npm run dev` starts.
- **Manual:** `git branch -a` in both repos, before and after, produces identical output.

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| A real secret is committed in `.env.example` | Low | **Critical** | Key names only; review `git diff --cached` before committing |
| The `!.env.example` negation accidentally unignores `.env` | Low | **Critical** | Acceptance criterion 4 verifies `.env` is still ignored |
| Deleting `dist/` breaks a teammate's running process | Low | Low | Local only; `npm run build` restores it |

## Rollback

Everything here is additive or local. Revert the commit to remove `.env.example`; run `npm run build`
to restore `dist/`. No shared state is touched, so nothing to coordinate.
